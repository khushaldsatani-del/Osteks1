# Project Memory — Osteks Coating Cost Calculator

Read this first in a new chat to pick up where things left off. This is a project handoff doc, not a design spec — for deep detail on a specific feature, follow the links to the dedicated docs.

## What this is

An internal tool for OSTEKS GmbH (coating/surface-treatment company) that:
1. Calculates coating costs from part weight/thickness/material/quantity, following formulas verified against a company spec PDF.
2. Lets a user upload **1 to 3** engineering drawings (PDF/PNG/JPG/TIFF) and, optionally, one related email (`.eml`/Outlook `.msg`) together in one drop zone — sorted automatically by file type, not separate upload steps. Each drawing goes to OpenAI vision AI **independently** (own extraction, own calculation, own Offer Details — see "Multi-image workspace" below) to extract manufacturing info (material, thickness, weight, coating spec, etc.); the email is **stored and linked only, never AI-processed**, and only stored at all if the first drawing's extraction succeeds — see "Documents/email persistence" below.
3. Renders a live "Angebot" (offer letter) preview matching the company's real quote-letter format, downloadable as PDF or an editable Word `.docx` — one pricing block per uploaded image.
4. Fully bilingual (EN/DE) — see "Translation (EN/DE)" below.

Git repo since 2026-08-20 (`main` branch, GitHub: `khushaldsatani-del/osteks`) — `git log` is authoritative for what changed and when going forward; this file plus code comments cover the reasoning/context that commit messages don't.

## How to run it

**Frontend** (`frontend/` — split out from the project root 2026-08-20 specifically so `backend/` and `frontend/` can each be deployed independently, e.g. `frontend/` to Vercel):
```
cd frontend
npm install
npm run dev
```
→ `http://localhost:5173`

**Backend** (drawing extraction + all persistence — required for anything to survive a page refresh; the calculator UI itself still works without it, just non-persistently). Python (FastAPI) — was Node/Express originally, ported to Python in full (see `backend/README.md`'s "Notes on the Python port" for what changed and how it was verified):
```
cd backend
python -m venv .venv
.venv\Scripts\activate      (Windows)  —  or  source .venv/bin/activate  (macOS/Linux)
pip install -r requirements.txt
copy .env.example .env
```
Then fill in `.env`'s `OPENAI_API_KEY` (https://platform.openai.com/api-keys — needs billing/credits, no free tier) and `DATABASE_URL` (a Postgres connection string — currently a Neon project; tables are auto-created on startup). Currently configured model: `gpt-5-mini` — see `backend/README.md`'s "AI provider history" section for why it replaced Gemini and how it was chosen, and `.env.example` for the token-limit/reasoning-effort settings.
```
python main.py
```
→ `http://localhost:5001`. Frontend calls it automatically; if it's not running, extraction/persistence just show an error (the calculator itself still works, un-persisted).

## Architecture

- **Frontend**: React 19 + Vite 8, plain CSS (no framework/Tailwind), no state library (component state + prop drilling / lifted state in `Documents.jsx`). `frontend/src/config.js` exports `BACKEND_URL`, shared by every component that talks to the backend.
- **Backend**: Python (FastAPI) in `backend/`. OpenAI vision API for drawing extraction (`/api/extract`, `services/openai_client.py` — replaced Gemini 2026-08-20, see `backend/README.md`'s "AI provider history" section). Postgres (Neon) via `asyncpg` for persistence — `documents` (one row per uploaded drawing, created right after extraction succeeds, updated by Calculation's Save with pricing/offer/calculation data) and `emails`/`email_attachments` (an optional `.eml`/Outlook-`.msg` file linked 1:1 to a document — **stored and parsed for display only, never sent to OpenAI or any AI**; see `backend/README.md`'s "Business rule" section). Client-side only for document export (no server involvement in PDF/Doc generation — `html2canvas` + `jsPDF` in the browser).

## Extraction accuracy: image pipeline + token budget (2026-08-21)

A real drawing was intermittently missing fields (weight, material grade, sheet thickness) that were clearly printed — root-caused two genuinely different problems, in this order, both found by actually logging Stage 1's candidate list rather than guessing (see `backend/prompts/extraction_prompt.py` and `backend/services/file_processing.py`):

1. **Image legibility.** A large sheet's overview gets downscaled to 2048px longest edge, and the generic tile grid (`MAX_TILES_PER_PAGE=4`, so at most 2×2 for a big sheet) still shares one tile between the title block and a lot of empty drawing-view space — confirmed live with a synthetic test at realistic scale: the model produced a plausible-looking but **wrong** digit-level OCR read (`13268` → `13208`) even with a "high-resolution" tile. Fixed with a dedicated, near-native-resolution **bottom-right corner crop** (`_tile_image`'s `TITLE_BLOCK_CROP_*` constants — 32%×28% of the sheet, only added when the sheet is large enough to need tiling at all, so zero cost on small drawings) — this app's real drawings (VW/EDAG-style) consistently put the title block there, matching DIN/ISO convention.
2. **Token budget — the bigger one.** `OPENAI_MAX_TOKENS_STAGE1`/`STAGE2` defaulted to 8192. `gpt-5-mini`'s hidden reasoning tokens draw from the *same* completion budget as the visible JSON/text output — confirmed by deliberately setting `OPENAI_REASONING_EFFORT=high`, which made Stage 1 **crash outright** (8192 tokens entirely consumed by reasoning, zero left to write any candidates). At the default `medium` effort the same crowding was happening silently: once the pipeline fix above added more images to reason over, fields near the end of the model's search would get cut from the candidate list with no error at all — this is why the very first fix (weight) appeared to work while others (material grade, sheet thickness) regressed. Raised to **16384** for both stages (`.env`, `.env.example`, and the code defaults in `openai_client.py`) fixed it — verified live with a combined test drawing (weight in the corner *and* material/thickness elsewhere) where every field came through correctly in one run. **Lesson for future prompt/pipeline changes**: adding images or instructions to this pipeline increases required output budget, not just input cost — check token usage logs (`_log_usage()` prints `prompt`/`completion`/`reasoning`/`total` per stage) for `finish_reason == "length"`-style crowding before assuming a prompt-wording fix is what's needed.

Also: the very first attempt at "search the whole drawing" prompt guidance was a large, repetitive addition (~12k chars) that actually made results *worse* on the real drawing — condensed to keep only the parts that measurably helped (whole-drawing-search directive, table-column-tracing with a worked example, the specific VW/EDAG weight-table sub-column pattern, label/abbreviation vocabulary, source-location requirement) and cut the rest. Longer isn't automatically better for this model — redundant instructions compete for the same reasoning budget as everything else.

## Multi-image workspace — 1 to 3 images per offer (added 2026-08-24)

The workspace went from strictly one drawing per session to up to 3, each with **fully independent** extraction/calculation/Offer Details. Core files: `frontend/src/pages/Documents.jsx` (owns an `images` array of up to 3 "slots" instead of flat singular state), `Calculation.jsx`/`OfferDetails.jsx` (each remounted per active slot via `key`, seeded from that slot's saved state, reporting changes back upward).

- **DB schema** (`backend/services/db.py`): `documents` gained `parent_document_id` (self-referencing FK, nullable), `image_slot` (1/2/3), and `offer_details_values` (the raw editable Offer Details fields, separate from the already-existing derived `offer_details_rows`). An offer's first image is a normal top-level row (`parent_document_id NULL`) exactly like every pre-existing single-image record already was — zero backfill needed, old records just work. Images 2/3 are child rows pointing at the first. `list_documents()` only returns top-level rows, so All Documents/Uploaded Files still show one row per *offer*, not per image. `GET /api/documents/{id}` (new) returns a parent plus all its child images in one call, for "Open in Workspace" hydration.
- **Upload flow**: drop/select up to 3 files at once — `UploadFile.jsx` extracts them **strictly one at a time, in sequence** (never parallel; this was an explicit requirement so per-image extraction accuracy never depends on batch size), reporting each file's start/result/error with its index in the batch. `Documents.jsx`'s `handleBatchStart` works out which slot each index lands in (prefers the active slot if it isn't already a success, then other idle slots, then creates new ones up to 3) **before** any extraction starts, so the pager already shows the right tab count immediately. The workspace **auto-switches the active tab** to whichever image is currently extracting, so the user visually watches each one populate in turn.
- **Save saves every slot in one action**, not just the active tab — this was a real bug (see below) and is now the deliberate design: the user sees one "Save" button for the whole offer.
- **Real bugs found and fixed** (all confirmed via synthetic multi-image test uploads, same methodology as the extraction-accuracy work above):
  - *Save only persisted the active tab.* The user clicks Save once, typically after finishing on the last tab — but the DB write only happened for whichever slot was active at that moment, so tab 1's Norm/Price/Quantity (which the All Documents row is read from, since it's always the parent row) silently stayed at defaults, and tab 1's Weight/Thickness/etc. never made it to the database at all. Fixed by having Save iterate every slot and persist each one's already-mirrored-upward state (`Documents.jsx`'s `handleCalculationSave`/`saveOneSlot`), parent (slot 1) saved first since children need its id as `parentDocumentId`.
  - *Save payload silently downgraded precision.* `{...values, notes, ...results}` — spreading the calculation engine's raw, full-precision `results` object *after* the already-correctly-rounded `values` (e.g. "0.5494") let it clobber those fields with unrounded numbers (e.g. "0.5493877551020409") in what actually got saved. Invisible live (every input reads from `values`, never `results`) — only showed up after a save+reopen. Fixed by flipping the spread order (`{...results, ...values, notes}`) everywhere this payload gets built — see `calculationDefaults.js`'s `computeCalcResults` and its two call sites.
  - *Reopening a saved record restored tab 2/3 correctly but not tab 1.* `Calculation`/`OfferDetails` only ever re-seed their form state from props at mount time (deliberately — a slot switch must never let a stray prop update clobber what the user is typing). Tab 1 is already showing the instant hydration data arrives (it's the default active tab), so its `key` never actually changes and it never remounts to pick up the freshly-loaded data — tabs 2/3 *do* get a genuine remount the first time the user clicks them, by which point the data has already loaded. Fixed with a `hydrationVersion` counter, bumped every time "Open in Workspace" hydration completes and folded into every slot component's `key`, forcing a remount of whichever tab is currently showing too.
  - *Weight/Thickness/Offer-Details auto-fill from AI extraction didn't always reach the form.* Same root cause as above, different trigger: during the auto-switch-through-tabs batch upload, a tab can become active — and its `Calculation`/`OfferDetails` mount — *before* that image's own extraction has actually finished, so the mount-time seed has nothing to fill in yet. Fixed with a safety-net `useEffect` in both components that fills a field **only if it's still at its untouched default** once the real extraction data arrives as a later prop update — never overwrites something the user already typed.
- **A genuine React footgun hit along the way**: `UploadFile`/`Calculation`/`OfferDetails` were all keyed `key={activeSlot}` — same key *value* on differently-typed sibling elements. React's keyed reconciliation isn't scoped by element type, so this caused a real, reproducible bug (confirmed with mount/unmount tracing, survived a production build so it wasn't a dev-only artifact) where the old Calculation instance never actually unmounted on a slot switch, leaving a second, stale copy in the DOM. Fixed by giving each sibling a distinct key prefix (`calc-${activeSlot}`, `offer-${activeSlot}`, etc.) — **always prefix keys uniquely per component when siblings of different types share the same underlying index.**
- **Processing steps (`ExtractionSteps.jsx`)** were also fixed here: a race where the batch's slot-mapping was computed as a side effect inside a `setImages` updater function (not guaranteed to run before the very next synchronous line reads it) meant image 1's loading steps sometimes silently never appeared at all. Fixed by computing the mapping synchronously, outside any state updater, before triggering extraction. Also made the steps feel less "stuck": they now progress through all 6 steps on a timer (previously hard-capped at step 5) and, if the real response still hasn't landed, the last step gets an animated ellipsis instead of sitting frozen.

## Documents/email persistence (added 2026-08-19, upload UX reworked 2026-08-21)

Every "All Documents" row is backed by the `documents` table — `App.jsx`'s `documentRecords` is fetched fresh from `GET /api/documents` (via `refreshDocuments()`, called after every create/update/status-change/delete) rather than held as local-only state. A document is created the moment `/api/extract` succeeds (`Documents.jsx`'s `handleExtractionResult`), *not* when Calculation's Save is clicked — Save only `PATCH`es that same row with pricing/offer/calculation data. This is why the All Documents row can appear before Save is ever clicked. The workspace's "Uploaded Files" widget is independently backed the same way (`Documents.jsx` does its own `GET /api/documents` fetch, mapped to that widget's lighter row shape) — real 5-rows-per-page pagination with blank filler rows to keep a constant card height regardless of record count, and a direct delete (trash) icon per row, not a dropdown menu (there was only ever one action, so the menu was removed 2026-08-21).

**`EmailAttach.jsx` no longer exists** — as of 2026-08-21 the drawing and its related email are picked in **one combined drop zone** inside `UploadFile.jsx` (multi-select file input, `accept` covers both drawing and email extensions), classified by file extension rather than by which slot they landed in. Dropping/picking a drawing still auto-starts extraction exactly as before; an email file found in the same drop (or picked separately, in either order) is just staged locally (`emailFile` state, lifted to `Documents.jsx` and passed down as a controlled prop) — nothing is uploaded yet. Only once `/api/extract` succeeds does `Documents.jsx`'s `handleExtractionResult` create the document row and then, if an email was staged, POST it to `/api/emails/upload` linked to that new document id. If extraction fails, the staged email is left alone (not cleared, not uploaded) so a retry doesn't force re-picking it — this is the actual mechanism behind "email only gets stored if the drawing succeeds." **Real bug hit and fixed here**: `handleExtractionResult` is invoked from a closure captured at the moment the drawing was dropped (often before the email gets picked), so reading `emailFile` state directly there silently saw a stale `null` — fixed with a `useRef` mirror (`emailFileRef`) that's always read fresh regardless of which render's closure ends up executing.

The All Documents Mail column (already existed, was always `"—"`) renders `✉ {subject}` when `mailEmailId` is present and opens `EmailDetailsModal.jsx` (From/To/CC/Date/Subject/Body/Attachments, each downloadable) on click — see `backend/README.md`'s Endpoints section for the full email API.

**Since multi-image (2026-08-24)**: an email always links to the offer's first (parent) image's document row, matching the DB's `emails.document_id` still being a plain 1:1 FK — no schema change needed there. **Firma Information's Enquiry Date auto-fills from the linked email's own Date header** (already parsed by the backend, no AI involved) the moment the email successfully links — only if the field is still blank, so it never overwrites a date the user already typed; with no email attached it just stays empty for manual entry, same as always (`Documents.jsx`'s `handleExtractionResult`, right after `setEmailStatus("linked")`). Fixing this surfaced a real, previously-latent bug: `firmaInfo` used to start as `{}` (no `enquiryDate` key at all), so the `<input type="date">` was uncontrolled until either the user typed or this auto-fill set it — React warns loudly when an input flips from uncontrolled to controlled. Fixed by seeding `firmaInfo`'s initial state (and its "Open in Workspace" hydration merge) with all four keys explicitly defaulted to `""` up front.

## Page structure (top to bottom in `frontend/src/pages/Documents.jsx`)

1. **Upload File** / **Uploaded Files** (`frontend/src/components/Upload/`) — one combined drop zone for up to 3 drawings plus one optional related email (see above), auto-starting AI extraction the moment drawing(s) are classified. A `?` (`CircleHelp`) icon fixed to the card's top-right corner opens `UploadInfoModal.jsx`, a static explainer of supported formats and what happens next.
2. **Extracted Drawing Details** (`frontend/src/components/Extraction/ExtractionPreview.jsx`) — shows the active slot's AI text summary once its extraction succeeds. While loading, shows `ExtractionSteps.jsx`, a 6-step horizontal progress indicator (Uploading → Preparing drawing → Reading drawing (AI) → Cross-checking values (AI) → Compiling results → Finalizing). **Still a timed frontend approximation, not real backend telemetry** — the backend runs extraction as one blocking request with no progress channel to the browser — but as of 2026-08-24 it now progresses through all 6 steps on a timer (no longer hard-capped at step 5) and, if the real response is still pending once it reaches the last step, shows an animated ellipsis rather than sitting visually frozen; the whole thing is still replaced by the real result (or error) the instant the actual response lands. True step-by-step streaming would need an SSE/WebSocket + job-tracking rework, not done.
3. **Calculation** (`frontend/src/components/Calculation/`) — the core cost-calculation UI: Firma Information (shared across all images of the offer), Extracted Details, Revenue Metrics, Pricing Analysis & Machine Loading, For Information — all per-image except Firma Information. See "Calculation engine" and "Multi-image workspace" above.
4. **Offer Details** (`frontend/src/components/OfferDetails/`) — a secondary form (Teilebezeichnung, Zeichnungsnummer, etc.), per image, with some fields auto-mirrored from that image's Calculation (Schichtdicke, Jahresmenge, Preis Beschichtung, Preis Maskierung — read-only, synced via `onSyncOfferFields` callback prop chain). Its `FIELDS` array entries carry a field *key*, not a hardcoded label — labels are resolved through the translation dictionary at render time (see "Translation" below), which is also why a saved offer's preview always shows in whichever language is currently selected rather than whatever was active when it was saved. A price/quantity field whose value is exactly 0 is omitted from the Document Preview/export entirely (0 means "not entered", not "free") — the 0 itself stays in the form/database untouched, only the preview hides it.
5. **Document Preview** (`frontend/src/components/DocPreview/`) — the offer-letter preview + PDF/Doc download, one pricing block per uploaded image (a small "Document N" label appears above each block only when there's more than one — a single-image offer renders byte-identical to before). **Full design doc**: `frontend/src/components/DocPreview/OFFER_DOCUMENT.md` — read that before touching this feature, it documents ~8 hard-won Word-export gotchas.

Plus `frontend/src/components/Sidebar/` (nav) and `frontend/src/components/common/CustomSelect.jsx` (a custom-built dropdown — native `<select>` popups can't be restyled with CSS, so Density/Beizen/Gußteil in Extracted Details use this instead; actively used, not dead code).

## Calculation engine (`frontend/src/components/Calculation/`)

- `calculationEngine.js` — pure functions, formulas cross-checked against a spec PDF ("Final Documentation for calculation.pdf" — no longer in this repo, was a one-time reference during development).
- `Calculation.jsx` — owns most of the app's numeric state. Key pattern used throughout: **natural vs. override**. Most Pricing Analysis fields (`AUTO_SYNC_FIELDS`) auto-follow their calculated value until the user types into them directly (tracked via `useRef` touched-sets, not React state, to avoid re-render loops). Clearing a field back to empty reverts it to auto-follow — but only on blur, not on every keystroke, so the field can go visibly empty while the user is actively editing.
- All numeric inputs are `type="text" inputMode="decimal"` with a manual sanitizer (`format.js`'s `cleanNumericInput`), not native `type="number"` — native number inputs had a confirmed backspace bug where clearing didn't always work.
- Indian-numbering-system live formatting (`formatIndianDigits`/`formatIndianLive` in `format.js`) on Weight, Surface Area [mm²], and Quantity.
- "Gewicht pro Warenträger in kg" turns light red when > 695kg (hardcoded threshold in `PricingAnalysis.jsx`).
- `calculationDefaults.js`'s `computeCalcResults(values, touched)` is the one shared place this "blank out untouched auto-sync fields before feeding the engine" logic lives — both `Calculation.jsx`'s own live `results` and `Documents.jsx`'s per-slot Save (recomputing a *non-active* slot's results from its stored `calcState`) call this same function. If a new auto-sync-style field is ever added, it only needs to be taught to this one function, not duplicated.
- **`initialState`/`AUTO_SYNC_FIELDS` live in `calculationDefaults.js`, not `Calculation.jsx` itself** — deliberately: a file that exports a React component *and* plain constants/functions breaks Vite's Fast Refresh boundary detection and was confirmed live to cause a real duplicate-mount bug (see "Fast Refresh" in Conventions below). Keep any new shared constants/helpers in `calculationDefaults.js`, not inline in a component file.

## Translation (EN/DE) — added 2026-08-24

The sidebar's EN/DE toggle (`Sidebar.jsx`, bottom-left) used to be dead UI — a local `useState` that only changed its own button highlight. It now drives the whole app. No i18n library was added (two fixed languages, no plurals/ICU needed) — a small hand-rolled system instead:

- `frontend/src/i18n/context.js` — just the `createContext()` call, nothing else.
- `frontend/src/i18n/LanguageContext.jsx` — `useLanguage()` / `useTranslation()` hooks and the `t(key, vars)` lookup (dot-path keys like `t("offerDetails.preisBeschichtung")`, `{placeholder}` interpolation for dynamic strings, falls back EN → raw key on a miss so a gap is visible/diagnosable instead of crashing or rendering blank).
- `frontend/src/i18n/LanguageProvider.jsx` — the actual `LanguageProvider` component (wraps `<App/>` in `main.jsx`), owns the `language` state, persists it to `localStorage` (`appLanguage`). **`context.js`/`LanguageContext.jsx`/`LanguageProvider.jsx` are three separate files specifically to avoid mixing a component export with plain-function/constant/context-object exports in one file** — see the Fast Refresh note in Conventions; this bit the project twice already (`Calculation.jsx`→`calculationDefaults.js` first, then almost again here) so it's now a hard rule for this codebase, not just a one-off fix.
- `frontend/src/i18n/translations/en.js` / `de.js` — the dictionaries, one nested key per component area.
- **Every component that renders user-facing text calls `const { t } = useTranslation()`** and looks strings up rather than hardcoding them — this covers every screen (Sidebar, Upload, Extraction, Calculation + all its sub-cards, Offer Details, All Documents including the CSV export, the email details modal) plus the generated offer letter itself.
- **Offer Details rows store the field *key*, not a translated label** (`OfferDetails.jsx`'s `FIELDS` array + the `rows.push([key, value])` it feeds to Document Preview) — labels are resolved through `t()` at render/export time in `DocPreview.jsx`/`buildDocx.js`, not baked in when saved. This matters: without it, a record saved while the app was in German would show German labels forever afterward even if the user later switched to English and reopened it.
- **The offer letter's boilerplate content** (letterhead, salutation, spec/terms rows, disclaimers — the big static block) lives in `docPreviewContent.js` as `getDocPreviewContent(language)`, returning German or a professionally-written (not literal word-for-word) English version of the same shape. `buildDocx.js` takes a `language` param for the same reason. Company name, addresses, and the recipient's personal name are **never translated** in either language (facts, not language content) — only country-name suffixes like "(Germany)"/"(Deutschland)" do, since those are genuinely part of the letter's language.
- **Per explicit decision, €-amount number *formatting* (comma decimal separator) always stays German-style regardless of language** — `format.js`'s `formatEUR`/`formatNumber` were deliberately left untouched; only text/labels translate, not the numeral convention.
- `Stk` (Stück/pieces) is treated as a translatable unit (`common.unitPieces` → "Stk"/"pcs"), unlike `€`/`%`/`m²`/`mm`/`kg`/`g` which are genuinely language-neutral symbols and stay literal in the JSX.

## Conventions worth knowing

- No comments explaining *what* code does — only *why*, when non-obvious (a gotcha, a workaround, a constraint). Match that style in new code.
- CSS files use one-declaration-per-line with blank lines between rules (unusual but consistent throughout — match it).
- Prefer editing existing files/patterns over introducing new ones (e.g., new form fields follow the existing `calc-field`/`calc-list-row` CSS classes rather than inventing new styling).
- **Fast Refresh module boundaries are a real, confirmed source of bugs in this codebase, not just a lint nit.** A file that exports a React component *and* plain constants/hooks/functions breaks Vite's Fast Refresh boundary detection — this caused an actual, reproducible duplicate-mount bug (confirmed with mount/unmount tracing, and confirmed it survives a production build, so it's not merely a dev-server artifact) twice this project: once in `Calculation.jsx` (fixed by moving shared constants to `calculationDefaults.js`) and again while building the translation system (`i18n/context.js` / `LanguageContext.jsx` / `LanguageProvider.jsx` are three separate files specifically because of this). **When adding a new file that both exports a component and needs to share constants/hooks with other files, split them from the start** — don't wait for oxlint's `react-refresh` warning to prove it matters, it already has, twice.
- **Give React `key`s a component-specific prefix, not just a shared index.** Multiple sibling elements of *different* component types keyed with the same bare value (e.g. `key={activeSlot}` on three different components) can confuse React's keyed reconciliation — found as a real bug in the multi-image work (see above). Use `key={\`calc-${activeSlot}\`}`-style prefixes whenever siblings of different types share an underlying index/id.
